# extension/AGENTS.md

Chrome MV3 extension, built with WXT. Read [`../AGENTS.md`](../AGENTS.md) first for repo-wide rules.

## Scope

The extension is the **browser-execution surface**, and the only component that can reach a
retailer session. It:

- reads retailer order pages in the user's existing browser session, on an explicit gesture;
- extracts a bounded, sanitized subtree and sends it to the API;
- drives the return flow by executing validated actions against the live DOM; and
- holds the detailed workflow/session state and the latest safe checkpoint in
  `chrome.storage.local`.

It does **not** hold a carrier or retailer credential, call a carrier, or talk to a model provider.
Inference is the server's job; the extension sends a sanitized representation and validates what
comes back.

**The server only ever sees what the extension sends it.** There is no background job reaching into
a browser, and no credential anywhere that would make one possible.

## Commands

```bash
bun install          # runs `wxt prepare`, which generates .wxt/ types
bun run dev          # loads the extension with HMR
bun run build        # .output/chrome-mv3/
bun run zip          # release artifact — requires a concrete dashboard origin
bun run compile      # tsc --noEmit
bun run test         # builds, then runs vitest against source and built manifest
```

`bun` is pinned via `packageManager`. Don't introduce `npm` or `yarn` lockfiles.

## Rules specific to this workspace

- **The manifest declares `activeTab`, `scripting` and `storage` — nothing else at install.**
  (Repo rule 8.) `activeTab` grants access only on a user gesture, so the first run *cannot* inject
  on page load: the popup offers "Scan this page", and the standing host permission for that
  retailer is requested afterwards, in context, once the user has seen it work. Adding `<all_urls>`
  to "make the first run work" trades the product's entire review posture for a convenience.
  `tests/manifest.test.ts` asserts this against the built artifact and will fail if it drifts.

- **The model drives the return flow through a closed action vocabulary.** (Repo rule 9.) `click`,
  `select_option`, `fill`, `pause_for_user`, `report_stuck` — forced tool choice, so there is no
  path where attacker-influenced retailer DOM talks the model into an action outside that list.
  `fill` never targets a password, payment or file-upload input. Selectors are tried first; the
  model is asked only when they miss.

- **The extension must never hold a carrier or retailer credential.** Those live server-side only.
  If a feature here seems to need one, it belongs on the server.

- **`externally_connectable.matches` takes concrete host patterns only** — a bare host wildcard is
  rejected when the manifest loads — so the dashboard hostname is baked into a reviewed artifact
  and cannot change without a store re-review. The production origin is not chosen yet;
  `manifest.config.ts` defaults to `http://localhost:3000` and `bun run zip` refuses to build a
  release that still points there.

- **Raw and sanitized DOM are transient inputs, never durable fixtures or database models.** They
  are extracted, sent, and discarded.

## Gotchas

- **WXT refuses to build an empty `entrypoints/`.** That is why `background.ts` exists as a stub
  before the real worker is written. Don't grow it — it is a build requirement, not a foundation.

- **`.wxt/` is generated by `wxt prepare`,** which runs on `postinstall`. `tsconfig.json` extends
  the generated config, so typechecking fails on a fresh clone until `bun install` has run.

- **`manifest.config.ts` is a separate module from `wxt.config.ts`** so the manifest can be
  asserted without building. Pinning the extension `key` will edit it.
