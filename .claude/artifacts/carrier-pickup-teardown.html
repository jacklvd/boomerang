Decision brief · Boomerang returns agent

Carrier Pickup Teardown

Which carrier will let Boomerang book a porch pickup for a user who has no shipper account, no carrier login, and a return label the retailer printed?

25 Aug 2026 USPS · UPS · FedEx Specs read directly: USPS Carrier Pickup 3.1.8, UPS Pickup v2409
Recommendation

Build USPS only for v1. Everything else needs an account that your user does not have.

USPS is the single carrier whose pickup API carries no account identifier in the request at all — not a shipper number, not a CRID, not a payment token. The pickup is identified by the consumer's address and contact details, authenticated by your app's own OAuth credentials. That is exactly the shape Boomerang needs, and the pickup is free.

USPS Ship it  Free pickup, no per-user credential, free API, production-mirror sandbox. One gate: Carrier Pickup is not in the default access package, so file the access request today.
UPS Fast-follow  Workable via PaymentMethod 04 — bill the pickup to the retailer's 1Z return tracking number. But you must hold a UPS account to get credentials at all, and a rejected payment leaves you owing ~$9–15.
FedEx Don't integrate  associatedAccountNumber is required and is the account invoiced. There is no tracking-number payment path. Use the fedex.com guest flow through the headless browser you already run.
Criteria

What actually decides this

Boomerang's user is a consumer holding a retailer-issued prepaid return label. They will never have a UPS or FedEx shipper number, and asking them for one kills the product. So the ranking is driven by one question — whose account does the carrier need — and three tiebreakers: what the pickup costs the user, how fast you can get to a working production call, and whether you can test before you are approved.

Option A

USPS Carrier Pickup 3.0

The one that works

OpenAPI 3.0.1 · v3.1.8 · read from spec
Base URL
apis.usps.com/pickup/v3
Test URL
apis-tem.usps.com/pickup/v3
Grant
client_credentials
Pickup cost
Free
Surface
  • GET /carrier-pickup/eligibility — is this address serviceable? Returns the standardized address when it is.
  • POST /carrier-pickup — schedule. Returns a confirmationNumber and an ETag.
  • GET | PUT | DELETE /carrier-pickup/{confirmationNumber} — inspect, change, cancel. PUT and DELETE require the ETag, which is good for one hour or until it is used.
The finding

The entire SchedulePickupRequest body is this — and there is nowhere in it to put an account:

// required: pickupDate, pickupAddress, packages, estimatedWeight, pickupLocation
{
  "pickupDate": "2026-08-26",
  "pickupAddress": {
    "firstName": "...", "lastName": "...",
    "address": { "streetAddress": "...", "city": "...", "state": "..", "ZIPCode": "#####" },
    "contact": [ { "email": "user@example.com" } ]   // or SMS; 1-2 entries
  },
  "packages": [ { "packageType": "RETURNS", "packageCount": 1 } ],
  "estimatedWeight": 3,
  "pickupLocation": {
    "packageLocation": "PORCH",     // FRONT_DOOR | BACK_DOOR | SIDE_DOOR | KNOCK_ON_DOOR |
    "specialInstructions": "...",   // MAIL_ROOM | OFFICE | RECEPTION | MAILBOX | OTHER
    "dogPresent": false
  },
  "nextAvailablePickup": true       // auto-rolls to the next serviceable day
}
Why this settles the question. No accountNumber, no CRID, no MID, no payment token, no EPS reference. The pickup is bound to the consumer's address and their own email or SMS contact; the only thing authenticated is your app. A third party scheduling on a user's behalf is not a workaround here — it is the ordinary shape of the API.
Constraints that shape the agent
  • Carrier Pickup is not in the default access package. A new app gets “Public Access I” — Addresses, Prices, Locations, Service Standards, Shipping Options, Tracking, OAuth, UserInfo. Pickup requires a separate access request, and USPS itself warns of extended wait times. This is the critical-path item.
  • Postage must already be on the box. Free Package Pickup only covers packages with prepaid online postage affixed. Boomerang's browser step must produce a real label, not just a QR code, before the pickup call is legitimate.
  • It is a day, not a window. The carrier collects on their normal delivery round, Monday–Saturday. Same-day requests must land before 2:00 AM CT; you can book up to a year ahead. The guaranteed two-hour window is a different product — Pickup on Demand, ~$25.
  • Eligibility is address-specific. Always call /eligibility before promising a pickup, and keep drop-off copy as the fallback.
  • Legacy Web Tools (the XML ShippingAPI.dll endpoint and CarrierPickupScheduleRequest) was retired 25 Jan 2026. Ignore every tutorial that uses it.
  • Rate limits are murky: documentation has cited a 60/hour default, while observed Public Access quotas run far higher and vary per API. Assume you will need a quota increase before launch and ask for it in the same support ticket as access.
Fix the promise in SKETCH.md. The mock message says “tomorrow between 9 AM and 12 PM.” Free USPS pickup cannot promise that. Say “with tomorrow's mail delivery” and have the box out by the time the carrier normally arrives.
Option B

UPS Pickup v2409

Possible, on someone else's dime

OpenAPI 3.0.3 · read from spec

Test URL
wwwcie.ups.com/api
Grant
client_credentials, or auth-code + PKCE
Pickup cost
~$9.05 future-day, ~$14.75 same-day, or $0 via method 04
Surface
  • POST /pickupcreation/{version}/pickup — schedule. Returns an 11-character PRN.
  • POST /shipments/{version}/pickup/{pickuptype} — price it first (oncall | smart | both).
  • /shipments/{version}/pickup/{CancelBy} — cancel. Pending-status lookup needs an account number.
The lever

PaymentMethod is required, and its enum is where the whole decision lives:

CodeMeansUsable by Boomerang?
00No payment needed — free-pickup regionsOnly where UPS pickup is free
01Pay by shipper accountNo — requires the user's UPS account
03Pay by charge cardTechnically yes; you would carry raw PAN + CVV. Don't.
04Pay by 1Z tracking number — “the shipper agreed to pay for the pickup packages”Yes. This is the path.
05 / 06 / 07Check, cash, PayPalNot automatable
Method 04 is the retailer-pays path. Pass the return label's 1Z number in TrackingData — up to 30 per pickup, exactly 18 characters, and a tracking number already used to pay for a pickup cannot be reused. The Shipper block is genuinely optional when you are not billing an account, so no UPS number ever has to come from the user.
Catches
  • You still need a UPS account to get credentials. Creating an app on the developer portal makes you attach a UPS account number to the client ID — even for an integration that never bills it.
  • Set AlternateAddressIndicator: "Y": the pickup address is the user's home, not anything on your profile.
  • If method 04 is refused — the retailer's label is not a UPS Returns label, or the number was already consumed — the pickup either fails or falls to a paid method. Decide in advance which, and never silently charge.
  • The auth-code + PKCE flow exists and does let a third party act against a customer's own UPS login, with refresh tokens. It is the right tool for merchant integrations and the wrong tool for consumers, who have no UPS login.
  • Handing a prepaid-labeled box to a driver already at your door is free. A scheduled on-call pickup is not, unless the label covers it.

FedEx Pickup Request v1

Blocked at the account field

The blocker, in FedEx's own words: Create Pickup requires the “FedEx account number, which will be invoiced for the pickup.” There is no tracking-number or prepaid-label payment path. Somebody's FedEx account is billed, every time.
  • Billing your own account for every consumer pickup is a real cost line (~$4/package Ground on-call, capped around $20/week per account and location) and an operational mess to reconcile.
  • The legitimate multi-tenant route is the Compatible Service Provider program: csp_credentials plus a child key and child secret minted per customer through the Credential Registration API. That is a contract and a certification, and it still assumes the customer has a FedEx account. Consumers don't.
  • The sandbox is virtualized — responses are predefined and do not vary with your input, so it validates wire format and nothing else. Production requires supplying an account number and passing validation, which for some APIs includes label review.
  • The fallback that actually works: fedex.com offers guest pickup scheduling with no account, paid by card at the door-step of the flow. Boomerang already drives a headless browser for the retailer's return portal — extend that path rather than building against the API. Flag the fee to the user before you commit it.
Also considered

Shipping aggregators don't rescue this

The instinct is to let EasyPost or Shippo abstract the three carriers away. They can't, for a structural reason.

  • Both bind a pickup to a shipment you created on your carrier account. A retailer-issued return label is neither.
  • EasyPost pickups attach to a shipment ID or batch ID, and explicitly cannot be scheduled against an arbitrary tracking number.
  • Shippo's pickup endpoint covers USPS and DHL Express only, and requires a carrier_account object ID.
  • Net effect: an aggregator adds a per-label cost and a dependency without removing the account requirement. Go direct.
Risks

What could still go wrong

Schedule

USPS access approval is not on your critical path — it is your critical path.No amount of code moves it. The support form wants your CRID, consumer key, app name, and the URL you're calling. File it before you write the client, and ask for the quota increase in the same ticket.

Integration

USPS scope name is inconsistent in the spec.Every operation declares carrier-pickup; the security scheme block declares pickup. Request the token without assuming, and log the granted scope on the first successful call.

Product

Not every address is eligible.Eligibility varies by address, so a meaningful fraction of users will get a “no.” The agent needs a graceful second answer — nearest drop-off, or a paid UPS/FedEx pickup with the price stated — not an error.

Money

UPS method 04 can be refused.If the retailer's label isn't a UPS Returns label or the 1Z was already spent on a pickup, you are one fallback away from silently charging someone $9–15. Make the failure explicit and never auto-escalate to a paid method.

Legal

On-behalf scheduling is unobjected-to, not blessed.Nothing in the USPS API terms prohibits it, and USPS's own Package Pickup material frames the APIs as serving “you and your customers.” Still worth a written confirmation from USPS API support before you scale, and worth capturing explicit user consent per pickup either way.

Security

Don't take the card path.UPS PaymentMethod 03 wants a raw card number, expiry, CVV and billing address in your request body. Adopting it drags the whole backend into PCI scope for a $9 line item.

Next

Build path

Ordered because it genuinely is — step one gates everything after it, and it is the one thing that cannot be parallelized away.

  1. File the USPS access request today

    Create the USPS Business Account, create the app with Public Access I at cop.usps.com, then open a support ticket for Carrier Pickup API access plus a quota increase. Have the CRID ready — it's required on the form.

  2. Build the client against the spec while you wait

    The OpenAPI document is public and complete. Generate the models, write the eligibility → schedule → confirm flow, and stub the transport so it can be pointed at TEM the day access lands.

  3. Smoke-test against TEM with production credentials

    apis-tem.usps.com mirrors production and takes the same client ID and secret — only the base URL changes. Verify the ETag round-trip for change and cancel, since that's the part most integrations get wrong.

  4. Wire the agent tool with eligibility as a hard gate

    Never call schedule without a successful eligibility check first. Persist confirmationNumber and the ETag together — without the ETag you cannot cancel, and the user will want to.

  5. Rewrite the user-facing copy

    Drop the two-hour window language. Set the calendar reminder for before the household's normal delivery time, and require the printed label — not just the QR code — to be on the box.

  6. Fast-follow UPS behind a flag

    Open a UPS account, register the app, and implement method 04 keyed off detecting a 1Z return tracking number in the retailer's label. Price it with the rate endpoint first so you always know what a fallback would cost before offering one.
