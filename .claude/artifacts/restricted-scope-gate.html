The Gmail API route costs about $540 a year and two months of calendar time. What is left is Chrome Web Store review and a lot of other people's HTML.

Executive summary

Yes — a browser extension can read the pages the user has open, and doing so sidesteps the entire Gmail restricted-scope regime. A content script with a host permission reads the rendered DOM of any site it matches. No OAuth scope is involved, so there is no app verification, no CASA security assessment, no annual fee, and no 100-user cap. That is a real escape from a gate that otherwise costs roughly $540–$1,800 every year in perpetuity and six to twelve weeks before the first outside user can connect.

The more useful finding is that Gmail is probably the wrong page to read. Retailer "Your Orders" pages carry better data than receipt emails — authoritative order status, return eligibility, and the actual entry point to the return flow — and there is published, still-shipping precedent on the Chrome Web Store for exactly this technique. Amazon Order History Reporter and Amazon Order History Exporter both scrape order pages with auto-pagination and are live in the store today.

What you trade is not the absence of policy, just a different flavor of it. Chrome Web Store Limited Use governs all user data an extension handles, not only data from Google APIs, and it tightened on 1 August 2026: collection must now be strictly necessary to the disclosed single purpose, cross-purpose collection is prohibited, and every collection needs prominent disclosure. Boomerang's server-plus-Bedrock hop is what will draw reviewer attention — the precedent extensions all advertise that they run locally and send nothing anywhere. Diverging from that is allowed, but it has to be disclosed loudly and justified.

The calendar pillar does not need an API either. Google Calendar accepts a prefilled-event URL — render?action=TEMPLATE with title, dates, timezone, location and description in the query string. The extension opens it in a tab, Calendar renders its normal event-creation form already filled in, and the user saves. That path needs no OAuth scope and, because chrome.tabs.create requires no host permission merely to open a URL, no Google host permission either. Writing to the calendar is solved. Reading availability is the part with no clean answer, and the fix is a design change rather than a technical one.

Taken together the two pillars mean Boomerang can ship with zero Google OAuth scopes. There is no consent screen, no verification queue, no CASA lab, no annual revalidation, no 100-user cap, and no seven-day refresh-token expiry — and no unverified-app warning screen in the onboarding funnel. The entire Google compliance surface collapses to Chrome Web Store review. What replaces it is a different and more diffuse risk: every data source is now a DOM that someone else can redesign without telling you, and the number of those DOMs grows with every retailer you support. One thing genuinely does not survive the move. Truly passive monitoring gets harder, because a content script only sees what is actually rendered — "watch the inbox in the background" becomes "sync when the user visits, or when they click."

Background

Boomerang, as described in SKETCH.md, is a returns concierge. Its first pillar is passive monitoring: watch the user's inbox for e-commerce receipts, extract order dates and retailers, and track the 30-day return window. The stack is a Chrome extension for the front door, a FastAPI backend on EC2, and Bedrock for the model calls that parse receipts and drive tool selection.

Every one of those architectural choices interacts with Google's OAuth policy. The Gmail read is a restricted scope. The backend is what converts "verification" into "verification plus an annual audit." The Bedrock hop is a data transfer that the Limited Use policy governs. And the extension distribution model adds a second policy surface in the Chrome Web Store.

Partway through this research the framing changed: if Boomerang is a browser extension anyway, does it need the Gmail API at all, or can it simply read what is already on screen? That turns out to be the better question, and the first section below answers it. The Gmail API material that follows stays in the brief because it defines the cost of the road not taken — and because there is one scenario that forces you back onto it.

Reading the page instead of the mailbox

What a content script can actually see

Content scripts are the only part of a Chrome extension that can touch a web page's DOM. They run in an isolated JavaScript world — separate variables and functions from the page's own scripts — but they share the same live document, so they can read and modify everything the user can see. Access is granted per-site through host_permissions in the Manifest V3 manifest, or at runtime through activeTab plus chrome.scripting.

The key legal fact: this path involves no Google API and no OAuth scope. The Gmail restricted-scope regime attaches to scopes, and the security assessment attaches to apps that access Google user data "from or through a server" via those scopes. Read the rendered page and neither hook catches you. There is no verification queue, no CASA lab, no Letter of Validation, no annual revalidation, and no 100-user ceiling.

The bounded claim

What disappears is the Google API compliance regime. What remains is Chrome Web Store policy, which is a real review with real rejections — just a cheaper, faster, self-serve one with no third-party auditor and no recurring invoice.

Route A — read the Gmail web UI

A content script matched to https://mail.google.com/* can read whatever Gmail has rendered. Gmail's markup is obfuscated and changes without notice, which is why nobody hand-rolls selectors for it. InboxSDK, built and maintained by Streak and used in production by Streak, Mixmax and Gmelius, abstracts the DOM behind stable classes like ComposeView and thread/message views. Registering an App ID for production use is, in their words, "100% free."

Two limits matter more than the parsing difficulty:

  • You only see what is rendered. The thread list gives you sender, subject, date and a short snippet. Full message bodies exist in the DOM only once a thread is actually opened. There is no equivalent of a server-side search across the whole mailbox.
  • That kills passive monitoring as specified. The sketch's "runs in background, monitors Gmail" pillar assumes something can sweep 30 days of mail unattended. A content script cannot, unless it drives navigation through the user's authenticated session — which is where this technique stops being merely fragile and starts looking like the automated access Google's terms exist to prevent.

Route B — read the retailer's order pages

This is the stronger design and it barely involves Google. Retailer account pages — Amazon's Your Orders, and the equivalents at J.Crew, Target, Best Buy — are a better data source than receipt email in every dimension Boomerang cares about:

  • They are authoritative and current. A receipt email is a snapshot from purchase day; the order page knows about cancellations, partial shipments, delivery confirmation, and whether the item is still return-eligible.
  • They state return windows and eligibility directly, rather than requiring you to infer a window from a purchase date and a guess at the retailer's policy.
  • They are where the return flow starts. The agent has to land on this page anyway to drive the return. Reading it and acting on it are the same surface.
  • They carry structured line items — per-item names, prices, images — which is exactly what "return the blue sweater" needs to resolve against.

The precedent is unambiguous. Amazon Order History Reporter (source on GitHub) and Amazon Order History Exporter are both live Chrome Web Store listings that systematically fetch and parse order history pages, auto-paginate across years, and extract order dates, totals, order numbers and item names. This technique passes Chrome Web Store review and survives there.

Read the precedent's privacy posture carefully

Those extensions market themselves on running entirely locally: no order history leaves the browser, and permissions are limited to storage, downloads and scripting on Amazon domains. Boomerang deliberately does the opposite — it ships parsed order data to a FastAPI backend and on to Bedrock. That is permitted, but it moves you out of the reviewer's "obviously harmless" bucket and into the one where disclosure quality decides the outcome.

What replaces CASA: Chrome Web Store policy, tightened three weeks ago

The Chrome Web Store Limited Use policy covers all user data an extension handles, not only data received from Google APIs. Extensions may collect only what is necessary for the disclosed single purpose; transfers are allowed where "necessary to providing or improving" the service; advertising, data brokerage and credit decisions are prohibited; and human review is barred except for explicit consent, anonymized analytics, security investigation, or legal compliance. A compliance statement must be posted publicly on a site you control.

Google published a policy update on 1 July 2026 that took effect on 1 August 2026 — three weeks before this brief. Three of the four changes land directly on Boomerang's design:

Notably, the Chrome Web Store version of Limited Use contains no equivalent of the Workspace policy's model-training prohibition. The blanket ban on using user data to train or improve any model beyond that user's personalized one attaches to data obtained through Google APIs. Data an extension reads off a retailer's page is not covered by it. The sketch's "teach the model the pattern of order receipts" stretch goal, which the API route rules out flatly, becomes a question of what you disclose rather than a prohibition — though it remains a promise you have to keep to your users.

The review reality: single purpose and host permissions

Two Chrome Web Store mechanics decide how painful the listing is.

Single purpose requires one narrow subject matter or browser function. The quality guidelines FAQ names "comparison shopping" as an acceptable narrow focus and offers a directly analogous example: a shopping extension may have an action button showing recent deals and host access to find coupons on the store the user is browsing. "E-commerce returns" is the same shape, and Boomerang's features — find orders, track windows, drive the return, schedule the pickup — are all plainly downstream of it. This is defensible, but it must be argued in the listing rather than assumed.

Host permissions are the friction point. Boomerang wants many retailer domains plus possibly Gmail, and broad host permissions flag an extension for in-depth review and a longer wait. Declaring <all_urls> when the core function touches specific domains draws a "justify your use of the following permissions" response and often a return for revision. The mitigations are well established: prefer activeTab plus chrome.scripting for anything the user triggers, and move the long retailer list into optional_host_permissions requested in context — when the user first says "return the J.Crew order," ask for J.Crew then. That keeps the required manifest small, avoids the submission-time warning, and reads better on the install prompt.

The genuinely unsettled question

Whether reading Gmail's own web UI via content script breaches Google's terms is not clearly answered in public documentation. No Google policy located in this research prohibits it, and a well-known set of extensions has done it in production for a decade through Streak's own SDK. But those products also hold OAuth grants for their server-side work, so they are not a clean precedent for a scrape-only design, and Google's API terms are written around authorized access paths. Route B avoids the question entirely by not touching Google properties — which is one more reason to prefer it.

Calendar, without an API and without scraping

The mail pillar has a scraping answer. The calendar pillar has a better one: a documented-by-convention URL that makes Google Calendar do the work.

Google Calendar responds to a template link at https://calendar.google.com/calendar/render?action=TEMPLATE. It accepts text for the title, dates as a YYYYMMDDTHHMMSS/YYYYMMDDTHHMMSS pair, ctz for the timezone, plus details and location — all URL-encoded. Opening it shows the user their own Calendar with the event-creation form already filled in. They review it and click Save. This is the mechanism behind every "Add to Google Calendar" button on the web, it has been stable for well over a decade, and it requires no JavaScript, no SDK, and no credential.

Two properties make it a particularly good fit for an extension. First, chrome.tabs.create({url}) needs no host permission at all to open a URL — host permissions are required only to inject scripts, fetch a domain, or read sensitive tab properties like url and title. So Boomerang can write to Calendar while requesting nothing for google.com in its manifest. Second, the confirmation step is not friction, it is the consent moment. The sketch's UX already has a "ping" where the user learns a pickup was scheduled; the prefilled form is that ping, and it makes the agent's action reviewable before it commits.

For users who are not on Google Calendar, generate an .ics file instead. It is a plain text format the extension can build locally and hand to the browser as a download, and Apple Calendar, Outlook and Google all import it. Same shape of interaction, one more provider covered.

The part with no clean answer: reading availability

The sketch's Calendar Scheduler is specified to "read calendar, check availability against provider policy, create task." The write half is solved above. The read half has no scrape-free equivalent — there is no template URL that returns data, and calendar.google.com is a heavily obfuscated, virtualized single-page app whose DOM would be the most fragile surface in the entire product. Scraping it is technically possible and strategically unwise.

The better move is to design the requirement away. Let the agent propose a pickup window from the carrier's available slots rather than deriving one from the user's free time, and let the prefilled event form carry the proposal. When that tab opens, the user is looking at their own calendar, in their own timezone, with the proposed block rendered in place — they can see a conflict faster than any parser could, and moving the event is a drag. The human becomes the availability check, which is both cheaper and more accurate than the alternative.

What disappears when you use no Google APIs at all

It is worth stating the consequence plainly, because it is larger than it first appears. With Gmail read via content script and Calendar written via template URL, Boomerang requests no Google OAuth scopes. Everything in the next chapter — consent screen configuration, the verification queue, brand review, the CASA assessment, the Letter of Validation, the twelve-month revalidation clock, the 100-new-user lifetime cap, the seven-day refresh-token revocation — simply does not apply. Neither does the unverified-app interstitial, which is a real conversion cost during a POC that is easy to forget when tallying compliance in dollars. The sketch's onboarding step "grant extension access" reduces to the Chrome install prompt.

Two consequences point the other way and should be sized honestly. Risk concentrates in one place: Chrome Web Store review is now the only gate, and if it rejects the host-permission set or the single-purpose narrative there is no second distribution channel. And the architecture shifts. With no OAuth grant there are no server-side credentials, so the backend can never see anything on its own — every byte reaches FastAPI and Bedrock because the extension pushed it there. That is favorable for the Limited Use narrative, but it means the backend's role narrows to parsing, inference and orchestration over data the client supplies, and any feature premised on the server checking something while the user is away needs to be rethought.

The API route, and when it forces itself back on you

Everything below is the road not taken. Under the all-browser architecture none of it applies — but it is the cost of three specific decisions, and each one is reversible in the wrong direction. You are back here if truly unattended background monitoring becomes non-negotiable, if the server ever needs to reach a user's data without the extension pushing it, or if per-retailer parser maintenance outgrows the annual fee. Read it as a price list, and check it against the roadmap before promising anything that quietly requires it.

Common misconception

Vendor blogs frequently suggest downgrading from gmail.readonly to gmail.metadata to dodge the assessment. It does not work — gmail.metadata is equally restricted and triggers exactly the same CASA requirement. What it buys is a narrower data footprint and an easier story to tell a reviewer, not a cheaper process.

The clause that puts Boomerang in scope

Not every restricted-scope app needs the security assessment. The trigger, in Google's own phrasing, is that an app "accesses or has the capability to access Google user data from or through a server" must undergo an annual assessment by a Google-approved third party.

"Has the capability to" is doing the work in that sentence. It is not about whether you store mail — it is about whether your infrastructure could see it. Boomerang's FastAPI service on EC2 receives message content and forwards it to Bedrock for parsing. That is squarely inside the clause, and no amount of "we don't persist anything" changes it. The only Gmail architecture that plausibly escapes is one where message content never leaves the client, which the sketch's server-side agent loop rules out.

Architectural consequence

If avoiding CASA were the priority, the parsing would have to happen entirely in the extension, with only derived, non-Gmail facts (retailer name, order date, order ID) crossing to the backend. That is a real design — but it means running receipt parsing on-device rather than through Bedrock, which is a different product than the one in the sketch.

What CASA actually costs

Google delegates the assessment to the App Defense Alliance's CASA framework, built on the OWASP Application Security Verification Standard. Per Google's security assessment help page, apps are assigned an assurance level — AL1 (the lab reviews evidence and scan artifacts you submit, without touching your running app) or AL2 (the lab tests the live application, its deployment infrastructure, and its data stores directly). Assignment is Google's call, based on user count, requested scopes, and other risk signals. Once you land at AL2, you stay there. Commercially, labs sell these as "Tier 2" and "Tier 3."

Two numbers in circulation that will mislead you

The $15,000–$75,000 range appears on Nylas's verification blog. It reflects the pre-CASA regime, when Google required bespoke assessments from firms like Leviathan and Bishop Fox, and it still describes enterprise engagements. It is not what a small team pays for a standard Tier 2 today.

Orbis's tier mapping claims gmail.readonly lands in Tier 3 while gmail.modify stays at Tier 2, and that they picked gmail.modify to save money. Every other source contradicts this — both are restricted, gmail.modify is strictly broader, and Google's own docs describe only AL1 and AL2 with AL2 as the ceiling. Their cost and process detail is credible; their tier taxonomy is not.

Will Google even approve a returns concierge?

Restricted Gmail scopes are limited to app types Google has pre-approved. Per the Workspace user data and developer policy, the permitted categories are email clients with a compose/send/read interface; apps that enhance email for productivity purposes — explicitly naming CRM, mail merge, delayed sending, and "providing generative AI summaries"; and apps that use information from emails to provide reporting or monitoring services. Explicitly excluded: one-time or manual email export, storing non-email data in Gmail, and multi-account abuse patterns.

Boomerang reads as a monitoring-and-productivity app and should clear the category bar. But Google's own announcement of this policy carves out exactly Boomerang's shape for extra friction: users who allow apps to access mail "without their regular direct interaction (for example, services that provide reporting or monitoring to users) will be provided with additional warnings and we will require them to re-consent to access at regular intervals." A background agent is the archetype of that pattern. Plan for periodic forced re-consent as a permanent product constraint, not a bug.

The Limited Use policy and the Bedrock hop

Restricted-scope data carries Limited Use obligations that survive verification and apply to raw, aggregated, anonymized, and derived data alike. The load-bearing constraints for Boomerang:

  • Use must be visible. Data may only serve user-facing features that are prominent in the app's own interface. Background enrichment that never surfaces to the user is not permitted.
  • No advertising, ever. Restricted-scope data may never be used or transferred for ads of any kind, including personalized or interest-based.
  • Human access is presumptively prohibited, with narrow exceptions for explicit user consent, security investigations, legal compliance, and aggregated-anonymized internal operations. Debugging against real user mailboxes needs an explicit consent path.
  • No model training. The policy prohibits "transferring, selling, or using user data to create, train, or improve a machine learning or artificial intelligence model beyond that specific user's personalized model for the appropriate use case or user-facing feature."

Direct hit on a sketch item

The stretch goal to "teach the model the pattern of order receipt email / label / QR" is the prohibited case, if it means fine-tuning or improving a shared model on user mail. Per-user personalization is allowed; a model that gets better for everyone because it saw one user's receipts is not. Inference itself is fine — sending message content to Bedrock is a service-provider transfer, and AWS's no-training terms for Bedrock make that defensible — but it should be documented in the privacy policy and named in the verification submission, because reviewers ask.

The seven-day rule is specific and easy to miss: for an OAuth client with External user type and Testing publishing status, Google revokes refresh tokens after seven days unless the only scopes requested are openid, userinfo.email, and userinfo.profile. Any Gmail scope puts you in the revoked bucket. A demo built in Testing mode will work beautifully on day one and be dead on day eight, with every tester needing to re-consent.

The single highest-leverage move for the POC

Switch the OAuth consent screen to In production immediately, without submitting for verification. You keep the unverified warning screen and the 100-user cap — neither of which matters for a demo — and you escape the seven-day token revocation. Passive background monitoring becomes demonstrable. Spend the 100 slots deliberately: they are a lifetime allowance on that Cloud project and there is no way to get them back.

Other unverified-mode facts worth knowing: refresh tokens are also revoked when a user changes their Google password if the token carries Gmail scopes, and after six months of non-use. Google caps live refresh tokens at 100 per account per client ID, silently evicting the oldest. For push-based monitoring, users.watch plus Cloud Pub/Sub works while unverified, but the watch must be renewed at least every seven days regardless of publishing status, notifications are capped at one per second per user, and each watch call costs 100 quota units against a daily project budget in the hundreds of millions. API quota is not the binding constraint at POC scale; token lifetime is.

Analysis

The extension reframing is not a loophole, it is a better product. It is tempting to read "skip the Gmail API" as a compliance dodge, but the strongest argument for reading retailer order pages has nothing to do with policy. A receipt email is a stale snapshot; the order page is live state, it declares return eligibility rather than implying it, and it is the surface the agent has to operate on anyway. Boomerang's job is not to understand email — it is to understand orders. Email was only ever a proxy for that, and a lossy one. The compliance saving is a side effect of aiming at the right data.

Going fully API-free changes the shape of the risk, not the amount of it. Zero OAuth scopes removes a cost that is knowable, budgetable, and bounded — $540 a year and a queue you wait in once. What it buys instead is an unbounded maintenance liability spread across Gmail's DOM, Calendar's URL contract, and one parser per retailer, none of which are versioned, documented, or under any obligation to stay put. That is very likely the right trade for a POC, where the queue would eat the whole timeline and the parser count is small. It becomes a genuinely open question at scale, when the retailer list is long and a silent layout change means the product quietly stops noticing orders. Worth deciding consciously rather than by default: the API route is not gone, it is deferred, and the moment to reconsider it is when parser maintenance starts costing more than $540 a year of engineering attention.

The template-URL pattern is the cleanest thing in this design, and it generalizes. It works because it does not ask for access at all — it hands the user a prefilled form on a surface they already trust and lets them commit the action themselves. Every property that makes it attractive here (no credential, no scope, no DOM coupling, no permission prompt, and an audit point the user actually sees) is worth looking for elsewhere in the product before reaching for either an API or a scraper. It also quietly solves an agent-design problem the sketch does not address: how a user reviews what the agent decided before it takes effect.

The honest cost is the passive-monitoring pillar. The sketch's first act is an agent that quietly watches and surfaces return windows before the user thinks to ask. A content script cannot do that unattended — it sees only rendered pages. The realistic designs are a sync that runs when the user naturally visits a retailer's site, an explicit "check my orders" action, or a periodic prompt. All three are weaker than the sketch's promise, and the product should decide now which compromise it is making rather than discovering it during the demo. Notably, the Gmail API route does not fully rescue this either: monitoring-class apps are exactly what Google flags for extra warnings and forced periodic re-consent.

Chrome Web Store review turns on disclosure, not on technique. The precedent extensions survive because their story is airtight and simple: local only, nothing transmitted, three narrow permissions. Boomerang's story is longer — it reads order pages, sends parsed data to a server, and runs it through a model. None of that is prohibited, but every step needs to appear in the listing, the privacy policy, and the permission justifications, and the code has to match. Mismatches between stated and actual behavior are the fastest documented path to rejection. Budget real time for writing these artifacts; they are the deliverable that gets you approved.

Permission architecture is worth designing early. Choosing activeTab plus optional_host_permissions over a broad static host list is a one-hour decision at the start and a painful refactor later. It avoids the in-depth review flag, shortens the wait, and makes the install prompt far less alarming for a product whose entire value proposition requires trust.

The gate is cheap in dollars and expensive in everything else. Five hundred and forty dollars is a rounding error against a seed budget. The costs that actually bite are the six-to-twelve-week calendar delay before any real user can connect, the annual recurrence that never ends, and the architectural constraints the policy imposes on how Boomerang can use what it reads. Teams routinely budget for the assessment fee and get surprised by the other three.

The security assessment is testing your infrastructure, not your product. Both first-hand accounts describe findings that were entirely about deployment hygiene — CORS headers, TLS ciphers, security headers, external asset loading. Boomerang's Terraform-and-EC2 setup is where those findings will land. Running OWASP ZAP and Qualys SSL Labs against a staging environment early, and fixing what they surface, converts the assessment from a multi-round negotiation into a two-day formality. The questionnaire — 50 to 54 questions on encryption, authentication, data handling, and vulnerability management — is answerable in an afternoon if the infrastructure story is already coherent.

Verification pressure should shape the scope request now, not later. Reviewers reject over-broad scope requests, and the narrowest-necessary justification is a written artifact you will have to defend. It is worth asking seriously whether gmail.metadata can carry the MVP: sender identifies the retailer, the date establishes the return window, and subject lines routinely carry the order number verbatim. That covers "gather orders in the last 30 days and rank by urgency" without ever reading a message body. It does not reduce the compliance burden by one dollar, but it makes the verification narrative dramatically easier and shrinks the blast radius of a breach. Escalate to gmail.readonly only when body parsing proves necessary for return links and line items — and be ready to show why.

The monitoring pattern is a permanent product tax. Google has said in writing that apps accessing mail without regular direct user interaction get extra warnings and periodic forced re-consent. Boomerang is exactly that app. The design should assume a recurring re-authorization moment and make it feel like a feature — a monthly "here's what I tracked, keep watching?" check-in — rather than a mysterious permissions prompt that churns users.

For a POC, do nothing and publish anyway. This applies only if a Google OAuth scope comes back into play, which the current architecture avoids. Should one return, the correct posture for the next few months is to skip verification entirely, publish the consent screen to Production to preserve refresh tokens, keep the tester list under 100, and build. Start the verification clock only when there is a real launch date, because the twelve-month revalidation timer starts from the Letter of Validation — verifying too early means paying for a year you spend pre-launch.

Open questions

  • How stable is the Calendar template URL, contractually? It has worked for over a decade and the whole web depends on it, but it is a convention rather than a documented, versioned API surface. Nothing found in this research is a Google commitment to keep it working or to keep its parameters unchanged. The practical risk is low and the failure mode is graceful — a broken parameter yields an empty event form, not a wrong event — but it should be a monitored dependency, not an assumed one.
  • What does the product do when it needs to know the user is free? The recommendation above is to design the requirement away and let the user resolve conflicts visually in the prefilled form. That works for a single proposed pickup. It does not obviously work if the agent later needs to choose among slots, batch several returns, or reschedule without asking. Whether the no-read design holds as the scheduling logic gets more ambitious is untested.
  • How many retailers can you actually parse? The Amazon precedent extensions cover one retailer with a stable, well-studied layout. Boomerang implicitly promises J.Crew, Target, and the long tail. Each is a bespoke parser against an unversioned DOM that changes without notice. Nothing in this research establishes how many retailers are tractable or what the ongoing maintenance load looks like — that needs a spike against three or four real order pages before it becomes a roadmap commitment.
  • Does reading Gmail's UI breach Google's terms? Unresolved above, and it stays unresolved. If Route A is ever seriously considered, this warrants a direct read of the Google Terms of Service and, ideally, counsel — not an inference from what Streak has gotten away with.
  • How does Chrome Web Store review treat an AI-backed shopping agent in practice? The August 2026 update signals closer scrutiny of AI-adjacent extensions, but there is no published guidance on how reviewers weigh an extension that sends page content to a third-party model. Recent approvals and rejections of comparable extensions would be the best available evidence.
  • AL1 or AL2? Google assigns the assurance level and does not publish the criteria beyond "user count, requested scopes, and other application-specific signals." A pre-launch consumer app with a small user base most likely draws AL1, but this is unknowable until Trust & Safety makes contact, and it is the difference between roughly $540 and roughly $4,500.
  • Current lab pricing. The comparison table reflects 2024–2025 rate cards from secondary sources. Get direct quotes from TAC Security and one alternate before budgeting; rates and the availability of unlimited-revalidation plans move.
  • How durable is the aggregator path? Vendors market shared verified OAuth clients as a clean bypass, and Nylas documents it explicitly. Whether Google tolerates a consumer-facing product shipping under a vendor's consent-screen identity long-term is a judgment call the sources do not settle, and Google reserves the right to suspend apps that misrepresent identity.
  • Chrome extension specifics. None of the sources address how the 100-user cap and the unverified warning behave for an OAuth client distributed through the Chrome Web Store, or whether Chrome Web Store review adds its own restricted-scope gate. Worth confirming directly before committing to the extension as the primary distribution channel.
  • Real end-to-end timelines in 2026. Google says "several weeks" and vendors say six to twelve. Public developer-forum threads show restricted-scope submissions sitting for months. A search of recent developer forum posts for apps of comparable shape would sharpen the estimate.
