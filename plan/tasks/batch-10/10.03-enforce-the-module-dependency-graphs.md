#### Task 10.3: Enforce the module dependency graphs

**Prerequisites:** Task 8.5, Task 6.5
**Conflicts with:** None
**Parallel with:** Tasks 10.1, 10.2
**Package:** `server`, `extension`

**Objective:** Make the two dependency graphs in §2.1 and §2.2 enforced rather than documented, and
enforce them **from the Mermaid source** rather than from a transcription of it. §10 declined to
design this but recorded it as worth adding — this is that.

**Instructions:**
1. **Neither linter config is hand-transcribed from a graph; both are tied to the Mermaid blocks in
   `design/boomerang-low-level-design.md`.** A config written by reading a diagram is a second copy
   of the architecture, and this copy is *executable*: when it drifts it does not merely mislead a
   reader, it fails the build on an import the design permits and passes the build on one the design
   forbids. The plan already ran this experiment on the diagrams themselves. It kept its own copies
   of §2.1 and §2.2; one grew edges §2.1 never drew, the other dropped every one of §2.2's edge
   qualifiers while still calling itself "complete and prohibitive", and both copies have since been
   deleted in favour of a link — see this plan's **Package Dependency Graph** section. Hand-encoding
   here would reintroduce that defect one layer down, in the place where it is enforced.
2. **Add `scripts/module-graph.py` — one parser, two consumers.** It locates the fenced ` ```mermaid `
   block under a named `###` heading of the low-level design and returns the node table plus a list
   of `(tail, head, qualifier, solid|dotted)` edges. `flowchart` edge syntax is small: `-->`, `-.->`
   and the `-- "label" -->` form, over ids that may or may not carry a `["label"]`. Two rules make
   the parse trustworthy:
   - **Fail on any line inside the block that does not parse, rather than skipping it.** A skipped
     line in a completeness check is an edge silently permitted, which is the failure this task
     exists to prevent.
   - **Node ids resolve to package paths through an explicit map in the script, and that map must be
     exhaustive over the graph's node set.** The script fails when the graph names a node the map
     does not. A new node gets classified by a person; it never gets guessed.
   One script rather than a Python parser for the server and a TypeScript one for the extension —
   two parsers of the same syntax are the drift this task is removing. The extension consumes its
   JSON output.
3. **Extension (§2.2): GENERATE the config from the graph.** §2.2 is complete and prohibitive — an
   edge that is not drawn is not permitted — so the drawn edge set *is* the allowlist and generation
   loses nothing that hand-writing would keep. Emit `eslint-plugin-boundaries` rules to a committed
   `extension/eslint.boundaries.generated.json`, import it from `eslint.config.ts`, and give the
   script a `--check` mode that regenerates and fails on any difference, so a stale commit is a CI
   failure rather than a silent one. **The generator classifies edges by kind rather than treating
   them uniformly**, because §2.2 draws two kinds that are not imports and states so in prose:
   - Edges between two `src/` nodes, and from an `entrypoints/` node into `src/`, are **static
     imports**. These are the ones that become boundaries rules.
   - Edges into the two platform nodes — `chrome permissions and scripting APIs` and
     `chrome storage local` — are **calls into the browser**. They generate the monopoly rules
     instead: a restricted-syntax rule on `chrome.tabs`, `chrome.scripting` and `chrome.storage`,
     permitted only in the modules the graph draws that edge from.
   - The two edges between `entrypoints content` and `entrypoints background` are **`chrome.runtime`
     deliveries**, and no import crosses them in either direction, so they contribute no permission
     at all. Because the allowlist is closed, omitting them *is* the prohibition. If a future edge is
     ever drawn between two entrypoints the generator must fail rather than guess its kind.
   `src/types/` and `src/config.ts` are permitted from everywhere. §2.2 exempts them by a property
   rather than by fiat — neither imports anything, so an edge into a leaf constrains nothing — and
   the generator carries that property as the comment on the exemption.
4. **Server (§2.1): keep the contracts hand-written and ASSERT them against the graph.** §2.1 is
   deliberately **not** exhaustive: it draws the layering rule, and `main`, `prompts` and
   `middleware` are omitted because they sit outside that rule, not because importing them is
   forbidden. An allowlist generated from it would forbid legitimate imports on its first run, so
   generation is the wrong mechanism here even though it is the right one for §2.2. Write
   `server/.importlinter` by hand — a layers contract plus the two named prohibitions, `app.routes`
   may not import `app.carriers` or `app.bedrock`, and `app.services` may not import `fastapi` — and
   add `scripts/module-graph.py --check-server`, run in CI, asserting the two directions a
   non-exhaustive graph does support:
   - **No contract forbids an edge §2.1 draws.** §2.1 names this failure itself: an arrow drawn
     backwards "becomes a contract that forbids the import the code actually needs and permits the
     one it must never make." This is the assertion that catches it, in either document.
   - **No `forbidden` contract names a pair the graph draws**, and every module the contracts place
     in a layer is either a node in §2.1 or an entry in a declared exemption list carrying its
     reason — `main`, `prompts` and `middleware`, each omitted for a stated cause. That list fails as
     stale the moment the graph gains the node, the way this repo's other authored allowlists do.
   The reverse direction is deliberately **not** asserted. An import §2.1 does not draw is not
   thereby a violation, and pretending otherwise is precisely what generating from this graph would
   do.
5. **Say what cannot be derived, so the derivation does not hide it.** A linter sees module-to-module
   reachability. Three things in these graphs are finer than that and stay human rules:
   - **The edge qualifiers, which is where most of §2.2's meaning lives.**
     `POPUP -- "reads only" --> STORE` *is* the single-writer rule; a bare edge list turns it into
     "the popup may import `src/storage/`", which permits exactly the write the rule forbids. The
     same holds for the worker's `all egress` monopoly, the driver's `egress scan on the fallback
     payload` licence over `src/extract/`, the popup's `ics delivery only` edge, and §2.1's lone
     `declares the dependency` label. So: the generator **emits each qualifier verbatim as the
     comment on the rule it produced**, and the script carries a small authored table mapping every
     qualified edge to the thing that actually enforces it — a §8.2 test row, a §8.3 assertion, or an
     injected type (Task 4.7 supplies the read-only store type behind `reads only`). `--check` fails
     when the graph carries a qualified edge the table does not name, and when the table names an
     edge the graph no longer draws. An unenforced qualifier is the drift that already happened once.
   - **The narrowness of a licence.** The graph says `entrypoints/background.ts` may reach
     `chrome.tabs`; §2.2's prose says for *exactly two calls*, the one-shot `executeScript` and
     `chrome.tabs.create` for the calendar template. A lint rule can hold the holder set and not the
     call count. That half stays a test.
   - **Which §2.1 omissions are deliberate.** The graph does not record why a module is absent, so
     step 4's exemption list is authored, with a reason per entry, and is checked only for staleness.
6. Wire all of it into the test/lint scripts and into the `.github/workflows/ci.yml` repo job Task
   1.3 created, so a violating import, a stale generated config and an unenforced qualifier are three
   distinct CI failures with three distinct fixes.
7. Verify each rule fires by adding a violating import temporarily and confirming the failure, then
   removing it. Verify the *derivation* fires too: change the graph and confirm the check notices,
   then restore it — a generated config nothing re-derives is a hand-written config with extra steps.
8. Reference: Low-Level Design §2.1, §2.2, §10; this plan's Package Dependency Graph section;
   Task 4.7 (the injected read-only store type); requirements NFR-6.3, NFR-6.5.

**Verification:**

- `cd extension && bun run lint`
- `python3 scripts/module-graph.py --check` — exits zero: the committed boundaries config matches
  §2.2 edge for edge, every §2.1 contract agrees with the graph, and every qualified edge is named in
  the enforcement table.
- Regenerate and diff: `python3 scripts/module-graph.py --write && git diff --exit-code
  extension/eslint.boundaries.generated.json` — empty, twice in a row (emission order follows the
  graph's drawn order, so the generator is deterministic).
- Add `from app.carriers import ...` to a route — `lint-imports` fails; revert.
- Import `src/api/` from the popup — `bun run lint` fails, since §2.2 draws no such edge and the

- Delete `POPUP -- "reads only" --> STORE` from §2.2 — `--check` reports both the generated config as
  stale and that enforcement-table entry as naming an undrawn edge; restore it.
- Reverse one §2.1 arrow — `--check` reports a contract forbidding a drawn edge; restore it.
- CI fails on a stale `eslint.boundaries.generated.json` committed without regenerating.
